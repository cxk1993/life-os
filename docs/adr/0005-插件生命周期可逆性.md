# ADR-0005 · 插件生命周期的可逆性（effect 必须携带逆）

- **状态**：已采纳（2026-10-03，hermes 勘察 + 落地 + 回归测试）
- **决策者**：主人（令「你负责全修，然后再把所有东西整理到交接区」）
- **影响范围**：`core/registry.py`、`core/plugins/manager.py`、`core/plugins/activator.py`、`core/plugins/migrations.py`、`core/app.py`；**今后每一个插件的 `api/lifecycle.py` 钩子与每一条迁移**
- **相关**：ADR-0002（插件协议）、`docs/specs/` 插件框架规格；理论依据 arXiv:2608.25512

---

## 1. 背景

### 1.1 实盘病灶

主人实盘见过一个现象：**「路由全 404，但工具在列」** —— 插件清单里看得见、MCP 工具已暴露，点进去却 404。历史上有两条记录指向同一根因族：

- `countdown` 放进 `plugins/` 后从未挂载（09-23 交付、09-25 才补启动恢复）→ 路由恒 404；
- `pi-agent` 挂载失败期间被掩盖的老 bug（`f774f2d` 才修）。

### 1.2 代码级根因（三处，均为**可逆性缺失**）

| # | 位置 | 病灶 |
|:--|:--|:--|
| **L1** | `manager.enable()` | **部分提交**：状态先落 `enabled=True` → 跑迁移（失败静默吞 `except: log.warning`）→ 挂路由（失败写 `last_error` 但**状态仍是 True**）。三个 effect 全都没有逆，失败后留下「状态说已启用、路由却不在」的中间态。 |
| **L2** | `manager.disable()` | **顺序反了**：先 `_unmount` 再跑 `on_disable`。插件撤自己的东西时，它的路由**已经消失**。 |
| **L3** | `activator._last_error` | **只写内存**：进程重启即失忆；且启动恢复只读 `enabled` 不看 `last_error` → 失败插件每轮重启重试、每轮无声重复半提交（**永远不自愈**）。源码注释自己写着「plugin_state 落库**候**」。 |
| **L4** | `registry.mount()` | **孤儿路由**：`include_router` 可能**部分写入后**才抛（prefix 冲突、依赖注入签名错误）。此时路由已进 `app.routes` 却没人登记 → **永远无法 unmount**，「插件可禁用」被击穿。 |

### 1.3 为什么这是个「纪律」问题，不是三个「bug」

三者共用一个根因：**我们把 effect 当成了「一次调用」，而不是「必须能撤销的状态变换」。**

一个 effect 若没有逆，它的失败就必然留下中间态；而中间态会让系统状态与真实能力脱钩 —— 这正是「404 但工具在列」的成因。

## 2. 理论依据

**arXiv:2608.25512**《A Programming Paradigm for Spatiotemporal Composability》（北大 Yifan Shi / Wei Zhang + DeepSeek Tianyi Cui，2026-08-26）。论文把「动态组合」形式化为两个正交维度：

- **Temporal composability（时间）** —— 组件被移除时，它对共享环境的修改能否**完全、安全地回滚**；
- **Spatial composability（空间）** —— 组件能否声明、发现、解析彼此依赖，并在依赖变化时协调生命周期。

论文的核心构造 `effect: Γ → Γ × (Γ → Γ)`：**每个 context 变换都携带一个 runtime 持有的逆**；逆按应用顺序**逆序**施加（Theorem 16）即完成回滚。

论文给出的失效论证，几乎逐字命中我们的场景：

> *「每次自我修改都强制全量重启，丢弃所有进程本地累积状态……**更糟的是，一次错误的自我修改可能禁用掉「恢复所需的那个进程」**。」*

第 6.3 节《Access Control and Sandboxing》另有一段独立讨论，与本 ADR 的权限/沙箱部分呼应。

**论文的实现即 Cordis**（`cordiverse/cordis`，MIT，2022 年创建），工业验证来自 **Koishi** 聊天机器人框架（2019 起生产使用，生态 4,000+ 插件）。

## 3. 决策

### 3.1 核心纪律（今后所有插件与内核改动一律遵守）

> **★ 每个 effect 必须携带逆。提问句式：「它的逆是什么？在哪个状态上生效？」**
>
> **★ 失败时按「应用的逆序」回放逆（Theorem 16）。**
>
> **★ 逆只在「该 effect 被应用的那个状态」上生效即可**（论文 Definition 8 的 witnessed effect function）。

### 3.2 本次落地

| # | 改动 | 落点 |
|:--|:--|:--|
| **L1** | `enable()` 逆序补偿：`done` 作为 accumulator 累积已生效 effect 的逆，异常时 `reversed(done)` 回放；补偿自身失败**只记日志、不上抛**（不许掩盖原始异常） | `manager.enable()` + `_compensate()` / `_state_snapshot()` / `_restore_state()` |
| **L2** | `disable()` 改严格逆序：`on_disable → unmount`。迁移回滚**仍留在 `uninstall`** —— disable 语义是「停用」不是「删数据」 | `manager.disable()` |
| **L3** | 激活目击落库：`activator` 新增 `set_persist_hook` 注入通道（**本模块仍不 import db**，分层约定不破），由 `app.py` 注入 `manager.note_activation_error`；启动对账新增「上次留有错误→点名重试」与「恢复失败汇总点名」 | `activator` / `app.py` / `manager.note_activation_error` |
| **L4** | `mount()` 防护：`include_router` 抛异常时，按对象身份摘掉本次写入的 routes 片段再上抛，保证失败后 `app.routes` 与调用前**逐元素等价** | `registry.mount()` |
| — | 新增差分补偿原语：`recorded_versions()` / `rollback_versions()` | `migrations.py` |

### 3.3 ⚠️ 关键取舍：迁移的逆**必须是「本次真正执行的那几个版本」**

`run_migrations` 自带台账（`app_setting` 的 `migration.<id>.<ver>`），幂等且只增不改。因此一次 `enable` 的迁移 effect = **它本次真正执行的那几个版本**。

**绝不能**在 `enable` 失败时直接调 `rollback_migrations`（全量倒序 `downgrade`）—— 那会把历史迁移一并 drop，**删掉承载数据的表**，属于比原故障更严重的二次破坏。

这正是论文 Definition 8 的场景：**逆只需在「该 effect 被应用的那个状态」上生效**，不必是全状态通用的全量回滚。实现上取「执行前后台账差分」。

### 3.4 旧行为保留说明（避免误读为行为漂移）

`run_lifecycle_hook` 的两类失败仍按旧语义区分：

- **钩子抛异常** → 触发逆序补偿（新：回滚状态/迁移/路由），并上抛；
- **钩子只回报错误串（不抛）** → effect 已生效，**不回滚**，仅把错误写进 `last_error` 供 `health`/`readyz` 目击。

即：只有「抛异常」才算失败到需要回滚；「回报错误」是软失败目击。

## 4. 验证

### 4.1 回归测试

新增 `tests/test_plugin_reversibility.py`（6 例），每例都是**修复前必红**的判据：

| 用例 | 守护 |
|:--|:--|
| `test_enable_failure_leaves_no_midstate` | L1：失败后 `enabled` 必须是 `False` |
| `test_enable_failure_does_not_drop_pre_existing_table` | L1/§3.3：补偿**不得**回滚历史迁移（表不能被误删） |
| `test_disable_runs_hook_before_unmount` | L2：`on_disable` 执行时自己的路由必须**还在** |
| `test_mount_failure_leaves_no_orphan_routes` | L4：mount 失败后 `app.routes` 逐元素一致 |
| `test_activator_persists_error_to_plugin_state` | L3：激活失败必须写进 `plugin_state.last_error` |
| `test_activator_persist_is_optional` | L3：未注入通道时退化为纯内存，不抛错 |

### 4.2 负向验证（证明测试不是摆设）

把 L1/L2/L4 三处临时还原为旧实现后重跑，**三条测试精确变红**：

```
FAILED test_enable_failure_leaves_no_midstate
FAILED test_disable_runs_hook_before_unmount
FAILED test_mount_failure_leaves_no_orphan_routes
```

恢复修复版后全绿。**全量套件 `pytest tests/` exit=0。**

## 5. 遗留与后续

1. **启动恢复的「重试上限」未做** —— 当前失败插件每轮重启都会重试（现在至少会点名报警）。若要退避/熔断，需另开卡。
2. **`install()` 未做同等补偿** —— `install` 的失败面是「建表 + on_install + 挂载 + 状态」，同样是多个 effect 无逆。本次未动（改动面更大，且 `install` 仅 third-party 走），**建议后续按同一纪律补齐**。
3. **`uninstall()` 已是逆序**（`on_uninstall → unmount → rollback_migrations → 清状态 → 删文件`），本次未改，可作为正例参照。
4. **论文第 6.3 节（Access Control and Sandboxing）尚未细读** —— 与权限/沙箱设计可能有关联，留作后续输入。
