# ADR-0003 · MCP 与外部集成策略

- **状态**：已采纳（2026-09-18）
- **决策者**：主人 + 云昔
- **影响范围**：所有与外部系统交互的插件（T08 理财 / T09 复盘 / 未来的 AI 能力）、内核的对外能力暴露方式
- **相关**：ADR-0002（插件协议）、`contracts/plugin.schema.json`

---

## 1. 背景

主人提出：财务模块要与云服务器上的 **BeeCount Cloud** 联动、复盘模块要与本机 **Work-Review** 联动，
并问了一个关键问题：

> 「BeeCount 支持 MCP 调用，我们的人生管理系统需不需要兼容一下 MCP 调用？还是继续走 API 调用？」

调研后发现，两个外部项目**各自都同时提供 REST 与 MCP**：

| 项目 | REST | MCP | 部署位置 |
|:--|:--|:--|:--|
| BeeCount Cloud | ✅ 完整 OpenAPI（`/docs`） | ✅ 内置 server，PAT 鉴权（`/api/v1/profile/pats`） | **云服务器**（单 Docker 容器，8869→8080） |
| Work-Review | ✅ Localhost API（`127.0.0.1:47831`，Bearer Token） | ✅ stdio server | **主人本机**（Tauri/Rust 桌面程序） |

所以问题不是"选哪个协议"，而是"**什么场景该用哪个**"。

## 2. 决策

### 2.1 ★ 核心：REST 与 MCP 分层，不是二选一

> **REST/API 是「给程序用的接口」，MCP 是「给 AI 用的接口」。它们服务不同的消费者。**

| 调用方 | 协议 | 理由 |
|:--|:--|:--|
| 前端 ↔ Life-OS 内核 | **REST** | 确定、可测、有 OpenAPI、幂等、可缓存 |
| 插件 ↔ 插件 | **REST + 事件总线** | 同上；且插件之间不许直接 import（ADR-0002 硬规则） |
| **Life-OS → BeeCount** | **REST** | 它 `/docs` 有完整 OpenAPI，稳定、快、可写测试 |
| **Life-OS → Work-Review** | **REST**（本机 API，经桥转发） | 它有 20+ 现成端点，含日报导出 |
| **AI（Claude / Cursor / hermes）→ Life-OS** | ★ **MCP** | 这是"AI 协助写日记/检索/整理"的正门 |

**Decision 1**：Life-OS 内部一切照旧走 REST；**不依赖**外部系统的 MCP 实现
（它们改 MCP 不影响我们）。Life-OS 自己**要做的是一个 MCP server**——对外暴露能力，而非对内替代 REST。

### 2.2 MCP 不需要"预留端口"，需要"能力可声明"

`manifest.provides` 已经是能力声明（ADR-0002）。**MCP 工具就是它的映射**：

```
插件 manifest.provides        →   MCP tool
────────────────────────────────────────────────
calendar.event.write          →   create_event / update_event / delete_event
todo.item.write               →   create_todo / toggle_todo
notes.note.write（→ 文档树）   →   write_document
notes.note.read               →   read_document / search_documents
finance.snapshot.read         →   get_finance_snapshot
review.daily.read             →   get_daily_review
```

**Decision 2**：新增一个**内置插件 `mcp`**（不是内核模块），它读取各插件的 `provides`，
把它们映射成 MCP tools。

**判据（可机器验证）**：给 AI 加一个新工具，**只需插件的 manifest 里多一行 `provides`**，
不改内核、不改 mcp 插件。做不到就是设计错了。

### 2.3 鉴权：AI 不能拿主人的登录令牌

MCP server 面向 AI 客户端，必须用**独立的、可吊销的、可限定范围的凭证**：

- 沿用 BeeCount 的既有做法：**PAT（Personal Access Token）**；
- 存放在 `app_setting`（T04 已建）或独立表，**只存哈希**；
- 每个 PAT 限定 `scopes`（如 `doc:read` / `doc:write`），越权直接拒；
- 支持随时吊销；**所有经 MCP 的写操作都进 `audit_log`**（T04 已建）——AI 改了什么必须可追溯。

**Decision 3**：MCP 用 PAT，不用 JWT 登录令牌；写操作全部留审计。

### 2.4 云 ↔ 本机：方向必须是"本机主动连云"

网站在云服务器上，而 Work-Review / Obsidian / Windows 通知都在本机。
**云服务器不能主动连本机**（家庭宽带无公网 IP）。

**Decision 4**：`services/bridge/`（T07 已建成 865 行）从"笔记同步专用"**升级为通用本机代理**：

```
本机 bridge  ──主动连云（WS）──►  Life-OS 云端
   │                                  │
   ├─ 持有 Work-Review 的 token        ├─ 有提醒 → 推给 bridge → 弹 Windows 原生通知
   └─ 能调 127.0.0.1:47831            └─ 要日报 → 让 bridge 去调 Work-Review API
```

三条硬要求（总纲雷区 #9 的具体化）：
1. **心跳 + 指数退避重连**，断线自愈；
2. 前端必须明确显示「桥离线」，**不许一直转圈**；
3. 桥只做**被动的代理执行**，不做业务判断（业务逻辑留在云端插件）。

### 2.5 性能与信息密度：横切契约，不是某个插件的功能

**Decision 5**：把下列要求写进**模板包与所有前端卡的验收清单**（否则各写各的，拼起来还是慢）：

| 手段 | 用在哪 |
|:--|:--|
| 虚拟化长列表 | 日程时间轴、待办、笔记列表、交易流水 |
| 乐观更新 | 所有写操作（勾选、拖动） |
| SSE 而非轮询 | 桥状态、同步状态、提醒 |
| CSS transform/opacity 动画 | 窗口拖动、坞动画 |
| 骨架屏 + 悬停预取 | 窗口打开、页面切换 |
| 信息密度：网格 + 紧凑卡片 + 可折叠 | "一口气展示最多信息" |
| 首屏体积预算（gzip 后 < 250KB） | 验收清单 |

## 3. 后果

**正面**
- 三种消费者（前端 / 插件 / AI）各得其所，互不干扰；
- 新增 AI 能力**不改内核**（只加 `provides`）——与 ADR-0002 的判据一致；
- 外部系统换实现（REST→MCP 或反之）**不影响** Life-OS；
- 桥一次建成，后续所有"云要碰本机"的需求全部复用。

**代价 / 风险**
- 需要维护一层 `provides → tools` 映射（但它是声明式的、极薄）；
- PAT 的签发/吊销/审计是一套新东西，必须做对（否则 AI 有越权风险）；
- 桥是本机常驻进程 → **需要主人同意**（见 §4 待确认）。
